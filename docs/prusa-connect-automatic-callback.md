# Automatic Prusa Connect callback capture

Current status, 2026-11-04: **implemented and published on WebOrca 5070**, using a narrow TypeScript
adaptation of the PrusaSlicer Account form/callback behavior rather than deploying its Go bridge.
The default flow is email/password → optional OTP. WebOrca's server forwards credentials to Prusa
Account and intercepts the registered callback before fetching its page; DevTools is unnecessary.
The registered Connect client/callback, state and PKCE remain enforced. Manual callback completion
is available as a fallback; social/passkey authentication is unsupported.

## Dedicated Connect: the actual current route

The browser loads the adapter in [shell.html:601](/home/david/PrusaSlicer/src/slic3r-app-web-ui/shell.html:601), fetches `/api/browser-config`, and mounts it when `prusaConnectBridge` is present ([shell.html:683](/home/david/PrusaSlicer/src/slic3r-app-web-ui/shell.html:683)). The Node server advertises that configuration and dispatches bridge requests before static-file handling ([serve.mjs:244](/home/david/PrusaSlicer/web/serve.mjs:244), [serve.mjs:267](/home/david/PrusaSlicer/web/serve.mjs:267)). Its proxy permits fixed routes including `auth/start`, `auth/password`, `auth/otp`, and `auth/complete`, checks browser origin/Host, and forwards cookies and CSRF headers to a configured HTTP loopback backend ([proxy:4](/home/david/PrusaSlicer/web/prusa-connect-proxy.mjs:4), [proxy:13](/home/david/PrusaSlicer/web/prusa-connect-proxy.mjs:13), [proxy:29](/home/david/PrusaSlicer/web/prusa-connect-proxy.mjs:29)). Go mounts `/api/prusa-connect/`; its default listener is `127.0.0.1:8250` ([main.go:625](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:625)). **That loopback hop is internal transport, not the OAuth redirect URI.**

The current modal explicitly says passwords pass through this server and Google/Apple-only accounts need an Account password ([adapter:440](/home/david/PrusaSlicer/src/slic3r-app-web-ui/prusa-connect-bridge.js:440)). Its submit handler calls `start()` then `password(email,password)`; optional MFA calls `otp(code)` ([adapter:853](/home/david/PrusaSlicer/src/slic3r-app-web-ui/prusa-connect-bridge.js:853)). Requests use same-origin credentials and `X-CSRF-Token` ([adapter:139](/home/david/PrusaSlicer/src/slic3r-app-web-ui/prusa-connect-bridge.js:139)). Although the client exposes `complete(callbackURL)`, this normal UI uses the password/OTP path ([adapter:163](/home/david/PrusaSlicer/src/slic3r-app-web-ui/prusa-connect-bridge.js:163)). It opens no provider popup and requires no callback-copy UI.

The backend sequence is:

1. `POST auth/start` creates fresh random state and PKCE verifier, a five-minute pending attempt and S256 challenge. Its authorization URL uses the fixed Connect pair ([main.go:30](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:30), [main.go:242](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:242), [main.go:98](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:98)). Pending sessions are bounded to 256 and identified by a Secure, HttpOnly, SameSite=Strict cookie ([main.go:127](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:127)). Exact origin/Host and subsequent POST CSRF checks occur in Go too ([main.go:195](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:195), [main.go:283](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:283)).
2. `POST auth/password` requires that pending attempt and receives email/password. Go creates a separate upstream cookie jar, disables automatic redirects with `http.ErrUseLastResponse`, GETs Account authorization with the same registered callback, parses the login form, and submits credentials ([login.go:100](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:100)). It forwards hidden form CSRF or the Account CSRF cookie, plus Origin/Referer and `X-CSRFToken` ([login.go:237](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:237)). Credentials are request-local rather than copied into pending session state ([login.go:142](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:142)).
3. `advance` follows at most eight steps. On a redirect to the exact Connect callback host/path, it reads `Location`, rejects malformed/duplicate code or state, checks the pending state, consumes the attempt, and exchanges the code **without GETting the callback page** ([login.go:270](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:270), [login.go:396](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:396)). Exchange sends the unchanged registered `redirect_uri`, saved verifier, and fixed `client_id` to Account `/o/token/` ([login.go:314](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:314), [main.go:378](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:378)). Connect's browser callback script therefore has no opportunity to consume or hide this code in this path.
4. If an OTP form appears after password, Go retains the upstream jar/form and returns `mfaRequired`. `POST auth/otp` consumes that pending form, submits the supplied code, then uses the same redirect/exchange machinery ([login.go:147](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:147), [login.go:169](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:169)). This is generic one-time-code form handling, not proof of all TOTP challenges: recognized field names contain `otp`, `token`, or `code` ([login.go:693](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:693)). Email-code delivery is also possible.
5. Successful login seals access/refresh tokens and CSRF into an origin-bound AES-GCM cookie with Secure/HttpOnly/SameSite=Strict attributes; it clears pending state and the request's token copy ([main.go:156](/home/david/PrusaSlicer/web/prusa-connect-bridge/main.go:156), [cookie.go:42](/home/david/PrusaSlicer/web/prusa-connect-bridge/cookie.go:42)). The modal receives authentication status, not token JSON.

Supported continuations are deliberately narrow: one matching consent form can be authorized; the exact optional `/passkeys/offer/` “Not now” form can be deferred once, with matching raw page/action queries and constrained continuation ([login.go:369](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:369), [login.go:519](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:519), [login.go:295](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:295)). Actual passkey/WebAuthn authentication and social-provider login are not implemented by this HTTP form client; external redirects fail ([login.go:324](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:324)). Recognized CAPTCHA pages, multiple POST forms and unknown form shapes fail rather than being blindly submitted ([login.go:407](/home/david/PrusaSlicer/web/prusa-connect-bridge/login.go:407)).

## Pre-implementation WebOrca and the original reuse proposal

At research time, WebOrca's gateway defaulted to the registered Connect pair ([gateway](../wasm/app/gateway/prusaConnect.ts)). `/auth/start` stored a 15-minute pending verifier/state/redirect and returned the link; `/auth/complete` required a full callback URL and matching pending state/verifier, then exchanged with the stored redirect/verifier and configured client. The React UI then instructed Network recording and full-URL paste ([PrusaConnectLogin.tsx](../wasm/app/src/printers/PrusaConnectLogin.tsx)). These manual fallback contracts are retained alongside the automatic path. The user's rejected localhost:8175 redirect and rollback to the registered callback on 5070 were supplied context, corroborated by the [earlier report:9](prusa-connect-redirect-capture.md:9); no service configuration was read during research.

A plain browser popup or iframe cannot read/intercept another origin's navigation URL or response headers; a service worker does not acquire control over an unrelated origin's document. Browser `fetch` cannot turn another tab's authenticated redirect into readable `Location`: CORS applies and manual redirects are opaque. See the normative [same-origin model](https://html.spec.whatwg.org/multipage/browsers.html#cross-origin-objects) and [Fetch opaque-redirect response](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque-redirect). A cooperating callback page or privileged native host supplies the missing boundary. Rewriting the callback after issuance or merely running a localhost listener cannot change the provider's redirect registration.

**Original recommendation (superseded by the implemented TypeScript adaptation):** reuse the existing Go bridge behind WebOrca's same-origin gateway and adapt the login panel to `status → auth/start → auth/password → optional auth/otp`. The proposal reused `main.go`'s pending/session dispatch, `login.go`'s jar/form/redirect machinery, `cookie.go`'s sealed session, and the Node proxy/adapter contracts, preserving the registered Connect pair. That option avoided a second HTML login parser but needed a session adapter for WebOrca's token-based printer calls. The implementation instead adapts the bounded jar/form/redirect behavior in [prusaAccountLogin.ts](../wasm/app/gateway/prusaAccountLogin.ts) and [prusaConnect.ts](../wasm/app/gateway/prusaConnect.ts), retaining WebOrca's token contract. The [UI](../wasm/app/src/printers/PrusaConnectLogin.tsx) now discloses backend password/OTP forwarding.

If preserving browser-native, OAuth-only credential entry is required, a local companion with a native WebView navigation hook could instead capture the **registered Connect callback** before its page loads and hand it to the pending WebOrca exchange. The native navigation-hook pattern above is reusable, but this Connect companion is not implemented or provider-validated by the inspected Account code; it also needs an authenticated local handoff bound to state/PKCE. Social login/passkey availability in embedded views remains a provider/platform constraint. A bare localhost redirect is not a demonstrated solution.
